## 受け入れ基準

### Phase 0 — L7 ルーティングと境界
- P0-1 `http://` は `https://` へ 301 で転送される
- P0-2 `https://app.localhost` で静的フロントが返り、セキュリティヘッダ（CSP・X-Frame-Options・nosniff）が付く
- P0-3 知らない Host 名には応答しない（default_server で切る）
- P0-4 ホストにポートを公開しているのは nginx だけ
- P0-5 nginx から API・Redis・DB へはネットワーク的に届かない（名前も引けない）
- P0-6 内部ネットワーク（app / backend / bff-data / auth-data）は `internal: true`
- P0-7 nginx の全公開ポートは `127.0.0.1` に限定される

### Phase 1 — BFF とセッション
- P1-1 未ログインで `/api/*` は 401
- P1-2 ログインでセッション Cookie `__Host-sid` が `HttpOnly; Secure; SameSite=Lax; Path=/` で付く
- P1-3 セッションの中身は Redis にあり、TTL が付いている
- P1-4 ログイン前に持っていたセッション ID はログイン後に使えない（固定攻撃の対策）

### Phase 2 — 自作 OIDC と JWT
- P2-1 `/bff/login` は PKCE(S256)・state・nonce 付きで認可エンドポイントへ転送する
- P2-2 誤ったパスワードではログインできない。登録されていない redirect_uri には転送しない
- P2-3 state が合わないコールバックは 400
- P2-4 ブラウザに返るもの（本文・Cookie）にトークンが含まれない
- P2-5 API は署名を JWKS で検証する。トークンなし・改ざん・別 audience は 401
- P2-6 ロールで認可する（bob=viewer は書き込み 403、alice=editor は 201）
- P2-7 認可コードは一回しか使えない

### Phase 3 — 運用で効く部分
- P3-1 アクセストークンの期限が近づくと、BFF がリフレッシュする（ブラウザは何もしない）
- P3-2 状態を変えるリクエストは CSRF トークンと Origin が合わないと 403
- P3-3 ログアウトで Redis のセッションが消え、以後 401。リフレッシュトークンも失効する
- P3-4 IdP の SSO セッションがあれば再ログインでフォームを出さない。IdP からもログアウトすると再びフォームが出る
- P3-5 どの層で止めたかが分かる（nginx の auth_request／BFF／API）
- P3-6 ログイン POST にレート制限（429）
- P3-7 nginx のアクセスログにはパスが残り、認可コード・state などのクエリ値は残らない
- P3-8 実 Redis でログアウトとリフレッシュを並行実行してもセッションは復活しない。期限切れ後の更新も拒否し、遅れて発行されたリフレッシュトークンも失効を試みる。Redis の読み込み・削除エラー時はログアウト成功や Cookie 削除を返さない

### Phase 4 — Keycloak
- P4-1 `make up-keycloak` で、BFF と API のコードを変えずに Keycloak でログイン〜API〜ログアウトができる

### Phase 5 — L4 とスケール
- P5-1 L4（stream）ポートは TCP をそのまま流すだけ: パスで振り分けず、nginx の auth_request も効かない（BFF の層で止まる）
- P5-2 BFF を3台にしても、同じセッションでどの台に当たっても API を呼べる

## 決めたこと

- サービスは Go の別モジュール（`services/api`・`services/bff`・`services/auth`）。ルートの `go.work` で束ねる
- 認証基盤は「最小の OIDC プロバイダ」として自作し、Keycloak と差し替えられる形にする
- 署名は ES256（自作）。Keycloak は RS256。API は両方を受け付ける（アルゴリズムは許可リストで固定）
- トークンの検証は `coreos/go-oidc` を使う（検証は自作しない。発行側だけ自作して学ぶ）
- ホスト名は `*.localhost`（`/etc/hosts` 不要）。ブラウザから見える URL（issuer）とコンテナ間の URL を分けて設定する

- この時点の指摘（下記の修正記録を参照）:
  - `compose.yaml` の 8080 / 8443 はホスト IP の指定がなく、localhost 限定ではない。手元専用なら L4 と同じく 127.0.0.1 に限定する。
  - `freshToken` と `logout` は同じ排他制御を使っておらず、更新中にログアウトすると、削除した Redis セッションを更新側の無条件 SET が再作成し得る。コード上の指摘であり、並行実行の再現テストは未実施。更新時の存在確認と保存を原子的にし、ログアウトとの競合テストが必要。
  - nginx のログが `$request_uri` を記録するため、コールバックの認可コードや state がログに残る。クエリを除く `$uri` か対象パラメータのマスキングを検討する。
  - `mkcert` 分岐は証明書を作るだけで CA の信頼登録を行わない。インストールだけでブラウザ警告が消えるわけではない。

### 2026-11-18 ローカル専用化・ログ・セッション競合の修正

- nginx の公開ポートをすべて `127.0.0.1` に限定。証明書マウントもサーバー証明書とその鍵だけとし、CA 秘密鍵はコンテナに渡さない。
- nginx のアクセスログを `$request_uri` から `$uri` に変更。P3-7 は一意のテスト値をコールバックのクエリに付け、パスが記録され、値が記録されないことを確認する。
- ログアウトは Redis の GETDEL で最新セッションの取得と削除を一度に行い、それから失効を要求する。リフレッシュ結果は SET XX で存在するセッションだけに保存し、削除後・期限切れ後の再作成を禁止する。保存できなかった新しいリフレッシュトークンも失効を試みる。
- P3-8 は内部ネットワーク上の実 Redis と専用テストコンテナで実行。トークン発行をチャネルで一時停止してログアウトを挟み、旧 Cookie の拒否・新旧トークンの失効要求・期限切れ・Redis エラーを確認。ホストへの Redis ポート公開はしない。
- 独立評価役に仕様のみ渡してレビュー。実装上の問題なし、Redis 障害時のテスト不足を指摘。GET / GETDEL の障害注入テストを追加し、500・成功URLなし・Cookie削除なしを確認した。
- 自作 IdP の `make verify`: `結果: 87 件成功 / 0 件失敗`。`make e2e-keycloak`: `結果: 72 件成功 / 0 件失敗`。切り替え直後の502を検出したため、nginx→BFF→API の実応答待ちを起動手順に追加して再検証した。Compose の待機にも180秒の上限を設定。最終の `make verify` も87件成功。追加の待機失敗処理は、3台化・1台化の各 Compose 呼び出しに失敗を注入して終了コード1になることを確認した。
- ブラウザ: 既存のアプリ内ブラウザで `alice` / 公開デモパスワードによるログイン、API 200、ログアウトで未ログイン、API 401 を確認。OS の信頼登録完了の証拠とは区別する。
- 証明書: CA 全体の信頼登録は macOS でキャンセルされ、再実行していない。ユーザーから影響について質問があり、信頼範囲を小さくする `make trust-local-cert`（サーバー証明書だけ、現ユーザー・SSL用）を準備。この時点では承認待ち（下記の登録完了記録を参照）。信頼設定はフォルダを削除しても残ることを README に記載。
