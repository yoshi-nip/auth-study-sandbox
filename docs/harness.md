# ハーネスの設計 — AI に「完成まで」任せるための仕組み

このリポジトリは、AI（Claude Code など）が人の承認を逐一待たずに実装を進められるように作っている。
そのための前提は「AI を賢くする」ことではなく、**間違えたら機械が止める環境**を先に用意すること。

## 全体の考え方（3行）

1. AI は自分の成果物に甘く、「できた」と早く言い、前の判断を忘れる。だから**合否を機械が返す**仕組みを先に作る。
2. 「注意して」と書くのは弱い。**例外のない決まりは機械で強制し、文書は地図と助言にとどめる**。
3. 外に出ると取り返しがつかない操作（push・リポジトリ作成・秘密の公開）は、**最後に人が止める**。

## 項目

各項目: **何を防ぐか／どこにあるか／外すと何が起きるか**。

### H1 短い地図 — `AGENTS.md`（`CLAUDE.md` から読み込む）
- **防ぐ**: 決まりを知らずに作る。長い指示が読まれず文脈を食う。
- **形**: 約40行。詳細は docs に誘導し、コードを読めば分かることは書かない。
- **外すと**: 毎回、決まり（ポートは nginx だけ・トークンをブラウザに出さない）を口頭で伝えることになる。

### H2 検証ループ — `make verify`
- **防ぐ**: 「できました」と言うが動いていない。
- **中身**: gofmt → go vet → 機密検査 → compose 構成の検査 → 単体テスト → **実際に起動して E2E**。
- **なぜ E2E が中心か**: このリポジトリの価値は「層の境界で本当に止まる」ことで、単体テストでは境界を確かめられない。
  E2E は**止まるべきものが止まる**（未ログインで 401、CSRF なしで 403、nginx から API に届かない）も確かめる。
- **外すと**: 人が毎回ブラウザで動かして確かめる。境界の穴が静かに残る。

### H3 完了の定義 — `docs/TASKS.md` の受け入れ基準
- **防ぐ**: 早すぎる完了宣言、都合のよい基準での完了。
- **形**: 各フェーズの基準を**作る前に**書き、基準ごとに E2E のチェックを対応させる（`scripts/e2e.sh` の見出しが基準の番号）。

### H4 状態の引き継ぎ — `docs/TASKS.md`・git の履歴とタグ
- **防ぐ**: 作業ごとに記憶が切れて、前の判断と矛盾したものを作る。
- **形**: 「今どこ・次何・決めたこと」を TASKS.md に一枚で持つ。フェーズの区切りで `phase-N` タグを打つ（学ぶ人も同じ順で追える）。

### H5 小さな単位 — フェーズごとのコミットとタグ
- **防ぐ**: 一度に大きく作って途中で崩れる。何が原因で壊れたか分からない。
- **形**: フェーズごとに `make verify` を緑にしてからコミットする。

### H6 機械による強制 — git フック・PostToolUse フック・CI
- **防ぐ**: 例外のない決まり（秘密を載せない・書式）が、文章だけで破られる。
- **形**:
  - `.githooks/pre-commit` → `scripts/check-sensitive.sh --staged`（秘密鍵・`.env`・JWT・個人のパス・example.com 以外のメール）と gofmt
  - `.claude/settings.json` の PostToolUse で、Go を編集したら gofmt を自動でかける
  - `.github/workflows/ci.yml` で `make verify` 相当（フックを入れていない clone の最後の砦）
- **なぜコミット前か**: 公開リポジトリでは、push した秘密は履歴から消しても回収できない。
- **限界**: 実名のように形で見分けられないものは人が見る。

### H7 権限 — `.claude/settings.json`（allow / deny / ask）
- **allow**: make・go・docker compose・curl・ローカルの git（add / commit / tag）。ここが広いので**人の承認なしに完成まで進められる**。
- **deny**: `.env` と鍵の読み取り、`--no-verify`、フックの付け替え、破壊的な `rm`。AI が自分で検査を外せないようにする。
- **ask**: `git push`・`gh repo create`・ボリューム削除など、外に出る／取り返しのつかない操作。
- **限界**: 文字列の一致なので万能ではない。だから秘密はそもそも `.env`（gitignore・ランダム生成）にしか置かない。

### H8 独立した評価役 — `.claude/agents/reviewer.md`
- **防ぐ**: 書いた本人のレビューだけで、認証の穴が通る。
- **形**: 仕様とコードだけを渡し、書いた側の説明は見せない。読み取り専用。「問題がなければ問題なし」と言わせる。
- **使う時**: 認証・セッション・トークン・Cookie・ネットワーク境界を変えたとき。結果は TASKS.md に記録する。

### H9 無人で進めるときの止め方
- **完了の定義**: `make verify` が緑。
- **触る範囲**: このリポジトリの中だけ。push・リモート作成はしない（ask）。
- **止める条件**: 同じ失敗を2回直して緑にならなければ止まり、原因と試したことを TASKS.md に書いて人に聞く。
- **やってはいけない直し方**: テストを消す・弱める、検査を外す、`ports:` を足して境界を迂回する。

### H10 見直し
- モデルが変わったとき・同じ失敗が2回起きたときに点検する。**指示を足すのではなく、検査かテストで止める**方向で直す。

## 採らなかったもの
- Stop フックで毎ターン `make verify` を強制する: E2E が数十秒かかり、短い質問にも走ってしまう。完了の定義として文書と CI で担保する。
- pre-push で `main` への push を止める: 個人の公開リポジトリで、push 自体を ask にしているため不要。
